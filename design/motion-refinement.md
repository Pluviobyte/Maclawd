# 主形态：精简与流畅度规划

对现有 38 个主形态动作做了一次全量测量，而不是凭手感。结论是
**该砍的比想象中少，该补的比想象中多**——问题不在动作数量，在每个动作的运动质量。

---

## 一、量化诊断

### 发现 1：运动密度只有像素动画下限的三分之一

以「姿态/秒」衡量（step-end 驱动的定格动画里，这就是流畅度的定义）：

| | 姿态/秒 |
| --- | --- |
| 当前中位 | **1.56** |
| 当前最低（`paused`） | **0.33**（6 秒 2 个姿态，等于一张静止图） |
| 像素画待机循环的通常下限 | 4 |
| 传统有限动画「三格一拍」 | 8 |

46 个状态类里 **21 个低于 1.5 姿态/秒**。这是「动作看起来僵」的首要原因，
而且和时长无关——`delegating` 有 5 秒，却只有 5 个姿态。

### 发现 2：像素栅格失配，轮廓每移动一格就抖一次

主形态窗口 128px，取景 45 单位 → **2.844 px/单位**，不是整数。

后果：1 单位宽的矩形（腿、眼睛）会因落点不同被渲染成 2px 或 3px。
45 个整数单位位置里，**7 个渲成 2px、38 个渲成 3px**。
角色每做一次整数单位位移，轮廓宽度就变一次——看起来像在呼吸/抖动。

| 窗口 | px/单位 | 1 单位矩形的实际宽度 |
| --- | --- | --- |
| **128px（当前）** | 2.844 | 2px×7 / 3px×38 ← 不一致 |
| 90px | 2.000 | 2px×45 ✓ |
| **135px** | 3.000 | 3px×45 ✓ |
| 180px | 4.000 | 4px×45 ✓ |

Retina 2× 下同理（256÷45 = 5.689 不一致；270÷45 = 6.000 一致）。

QA 尺寸档 64 / 96 也不是 45 的整数倍（1.422 / 2.133），
所以历次 QA 截图看到的都是带抖动的版本。

**mini 是 48÷16 = 3.000，本来就是干净的**——这也是为什么 mini 的截图看着比主形态利落。

### 发现 3：没有缓动，全是匀速

定格动画的「缓动」不靠插值，靠**不均匀的保持时长**：
极端姿势多停几拍，中间姿势快速掠过。

测量 36 条身体动画的保持时长变异系数：

- 中位 **0.18**
- **31 / 36 低于 0.35**（等于匀速）
- `moving-body` 是 `[20, 20, 20, 20, 20]`——完全等分，匀速的教科书定义

匀速位移是「机械感」最直接的来源。这一条**不需要新增任何姿态**，
只是重新分配百分比，成本几乎为零。

### 已经做对、不要动的两件事

- **图层错相**：38 条里 **37 条**的身体 / 爪 / 眼 / 道具已经踩在不同的拍上。
  只有 `building` 是全同步。这块不是问题。
- **`step-end`**：对像素画是**正确**选择。见下方「为什么不改成插值」。

## 二、精简：38 → 30

判据是**这个动作是否为「一眼看懂 Claude 在做什么」贡献了独立信息**，
不是「好不好看」。用户明确要求保留的睡眠链（`away` / `sleeping` / `waking`）全部保留。

### 砍掉：不可达（3 个）

| 动作 | 证据 |
| --- | --- |
| `moving` · Sideways Scuttle | 外壳从不发 `shell.move`（Swift 里只发 7 个 shell 事件）。拖动已被 `interaction.drag` + `interaction.drop` 完整覆盖 |
| `ambient.notification` · Attention Turn | 外壳从不发 `shell.notification`。而且 macOS 通知不是 Claude 的状态，占用同一视觉通道只会稀释真信号 |
| `cancelled` · Tiny Shrug | Claude Code 不暴露「用户取消」信号（读了 60 个真实会话确认：`stop_details` 全为 null） |

### 砍掉：信息量不足（5 个）

| 动作 | 理由 |
| --- | --- |
| `working.reading` · Pocket Book | Read / Grep 毫秒级返回，修饰一闪而过。真机试跑时实测**看不见** |
| `working.writing` · Letter Note | 同上 |
| `working.syncing` · Spool Sync | WebFetch / git 频率低，与 `working` 无实质信息差 |
| `workspace` · Workspace Folder | 切工作目录是低信息事件，而且它以 oneshot 插播，会**打断**真正在演的动作 |
| `ambient.reconnecting` · Ready Wiggle | 「恢复了」不需要独立动作——回到之前的状态本身就是信号 |

**为什么 `recovering` 和 `owner_resolved` 保留**：它们要闭合各自的道具环
（篮子得被推开、罐盖得咔哒松开）。开了环不收，才是真的突兀。
`ambient.reconnecting` 没有开过任何环。

**为什么 `working.building` / `working.testing` 保留**：Bash 命令跑几十秒，
修饰有足够时间被看到；而且「测试在跑」是用户会据此决定等不等的信息。
这正好和被砍掉的三个相反——不是按「好不好看」留的，是按**能不能被看见**留的。

### 保留但重做

`paused` · Statue Pause 触发源真实存在（菜单栏暂停），但 0.33 姿态/秒是全套最僵的。
不砍，按下面的杠杆 2、3 重做。

## 三、流畅度：三个杠杆

### 杠杆 1 — 修像素栅格（一行改动，收益/成本比最高）

- 主窗口 `PetWindow(size:)` **128 → 135**（3.000 px/单位，Retina 6.000）
- QA 尺寸档 64 / 96 → **90 / 135 / 180**（全是 45 的整数倍）
- mini 48px 已是 3.000，不动

135 与 128 只差 7px，桌面上感知不到大小变化，但轮廓抖动会**完全消失**。

### 杠杆 2 — 提高姿态密度（主要工作量）

目标中位 **1.56 → 4 姿态/秒**。

| 类别 | 现有姿态数 | 目标 |
| --- | --- | --- |
| 循环类（loop） | 5–7 | 16–20 |
| 反应类（oneshot / transition） | 4–6 | 8–12 |

**时长一律不变**——契约锁定了每个动作的时长，改时长会连带影响状态机的驻留判定。
只在现有关键姿势之间补过渡姿势。

### 杠杆 3 — 用不均匀保持做缓动（几乎零成本）

极端姿势保持 2–3 拍，中间姿势 1 拍掠过。目标变异系数 **0.18 → ≥ 0.5**。

这一条不新增姿态，只重排百分比，但它决定动作是「机械地走位」还是「有重量地动」。

### 为什么不改成插值（linear / ease）

必须写进契约，避免将来有人「顺手优化」：

插值会产生**非整数单位位置**。在 3.000 px/单位下，0.5 单位 = 1.5 设备像素，
矩形边缘会落在设备像素中间 → 抗锯齿糊边，或者被 `crispEdges` 吸附时反复跳变。
两种结果都比现在更糟。

**像素画的流畅来自姿态密度与节奏，不来自插值。** `step-end` 是对的，保留。

## 四、实施顺序

1. **杠杆 1**（像素栅格）——独立、低风险，先做。同时更新 QA 尺寸档并重拍截图。
2. **试点 5 个动作**：`idle` + 3 个 idle 变体 + `working`。
   这 5 个占据桌面上绝大部分时间，做完就能判断杠杆 2、3 的效果值不值得铺开。
3. **精简**（砍 8 个）——同时更新 mini 收敛表；测试会挡住漏改。
4. **铺开剩余 25 个**，按出现频率排序：待机 → 工作 → 互动 → 生命周期 → 环境。

工作量集中在第 4 步：25 个动作各自重写关键帧。第 1、2 步加起来是一个下午的量，
而且第 2 步做完就能拿到判断依据。

---

## 五、需要机器守住的新不变量

现有测试守的是「素材存在、几何一致」，守不住运动质量。建议补：

- **姿态密度下限**：每个 loop 动作 ≥ 3 姿态/秒，反应类 ≥ 3.5
- **缓动**：身体动画的保持时长变异系数 ≥ 0.35
- **像素栅格**：所有渲染尺寸必须是取景单位数的整数倍
- **timing-function**：`.motion` 必须是 `step-end`，改成插值直接测挂
