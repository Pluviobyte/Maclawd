# 手机联动方案（预留，暂不实现）

状态：**已完成可行性与成本测算，主动搁置。** 先做纯本地方案，本文档保留结论，
避免将来重新调研。

## 为什么搁置

不是因为做不了或太贵，而是**先决条件没到**：Maclawd 目前连 macOS 应用都还没有，
桌宠运行时也没实现。在 Mac 端跑起来之前铺 iOS App + 推送基础设施，是把战线拉到
无法验证的地方。

## 两个需求

1. **实时任务通知** —— 电脑在跑，人去看手机，跑完了手机有提示
2. **手机端统计** —— 在手机上看用量

## 硬约束（已查证）

灵动岛第三方接入只有 ActivityKit / Live Activities 一条路，而它**只能通过 APNs
远程更新**。这意味着：

- **本地网络方案不成立。** iOS 后台应用无法可靠保持长连接——而「用户正在刷手机」
  恰恰就是 App 在后台的时候。Bonjour / Multipeer 在这个场景必然失效。
- **必须有服务器。** 这是 `token-tracking.md` 不可变原则 1 的一个新例外，
  需要独立开关 + 独立披露 + 默认关闭。

具体版本行为（push-to-start 最低系统版本、ActivityKit 更新配额、Live Activity
时长上限、APNs 包体上限）实现前必须按当期官方文档核实。

## 关键发现：可能根本不需要存用户数据

实测本机 113 天重度使用（6 个工具）的聚合体积：

| | |
| --- | --- |
| (天 × 工具 × 模型 × 项目) 单元 | 468 行 |
| 会话记录 | 452 行 |
| 入库体积（含索引） | **125KB / 113 天** |
| 折算 | **1.1KB/人/天**，33KB/月，0.4MB/年 |

**1.1KB/天 塞得进一个 APNs 推送包**（普通推送上限约 4KB）。所以统计数据可以走
推送通道直接送到手机，服务端一个字节都不用存，手机端本地留历史。

| 架构 | 服务端存用户数据 | 1000 人每人每月 |
| --- | --- | ---: |
| **A. 推送送摘要**（推荐） | 否 | ~1 分 |
| B. 云端存聚合 | 是 | 3–4 分 |

首次安装的历史回填（113 天 = 125KB）走局域网一次性同步或分片推送。

## 成本测算（1000 人）

推送量（Mac 端做「用户是否离开」门控，服务端不判断）：

| 模式 | 每人每天 | 每人每月 |
| --- | ---: | ---: |
| 仅告警 | 3–5 | ~150 |
| 灵动岛 + 进度更新（离开期间 30s 一次） | ~60 | ~1,800 |
| 不做门控、每轮都推（反面参照） | 164 | ~5,000 |

> 164 轮/天 是本机实测的**理论上界**（仅 Claude Code）。真按这个推会被卸载。

并发：

```
同步上行 48,000/天 + 手机读取 10,000/天 + 推送 66,667/天
= 125,000/天 = 1.4 请求/秒（平均），10–15 请求/秒（峰值）
```

一台最小 VPS 的百分之几。**并发从来不是这个项目的问题。**

年成本：

| 项目 | 年成本 |
| --- | ---: |
| Apple Developer Program | **$99** |
| 域名 | $12 |
| 计算 | $72 |
| 数据库（B 方案，自建 / 托管） | $0 / $300 |
| 备份 | $12 |
| APNs 流量 | **$0**（Apple 不收费） |

A 方案 ~$183/年 → **$0.015/人/月**；B 方案自建 $195/年、托管 $483/年 →
**$0.016 / $0.040 /人/月**。

**边际成本接近零，固定成本占绝对主导**，Apple 的 $99 一项就过半。
从 1000 涨到 10000 用户不用换机器。

## 钱不是主要成本

存了用户数据之后，真正贵的四样都不在账单上：

1. **合规与删除义务** —— 导出、删除、泄露通知，是持续责任
2. **备份与恢复** —— 丢用户半年统计是真实损失
3. **可用性依赖** —— 服务端挂了手机端就没数据，纯本地没这个问题
4. **口径漂移与回填** —— 这条最容易低估。本项目已经撞到两个真实的口径错误
   （Kimi 的 `step.end`/`usage.record` 双计、WorkBuddy 用 `id` 去重会少算）。
   **已上传的历史是按旧口径算的**，修好解析器后云端那份是错的，需要重算/回填机制。
   纯本地方案重扫一遍就好。

## 上传内容的红线

- 聚合数字、模型名 —— 可传
- **项目名 —— 会泄露你在做什么**，必须可关闭或哈希（vibecafe 的 `uploadProject`
  开关就是为这个）。数据层已把 `projectPaths` 分开存，上传时可只传 basename
- prompt / 代码 / 文件内容 —— **一律不传**（`token-tracking.md` 原则 2）

## 事件契约已经就绪

状态机产出的事件本来就是 push-ready 的，最高价值的两个是：

1. **`needs_owner`** —— 卡住等你决定。**这个比「完成」更值钱**：任务完成迟早会发现，
   一个权限框挂 20 分钟是纯浪费。`variants: ["permission","question","unknown"]`
   正好来自 hook 的 matcher
2. **`error` / `success`**

载荷只需要：状态枚举 + 项目名（可选）+ 时间戳。**不需要 token 数、不需要 prompt。**

## 第 0 步已实现：局域网只读镜像

不追求「离开时收到提醒」，只做「主动打开手机看一眼」。这样**不需要 APNs、
不需要服务器、不需要 Apple 开发者账号**，成本是零。

```
maclawd-usage serve          # 面板里开启「局域网只读镜像」后重启
→ http://<局域网地址>:4173/mobile?t=<配对令牌>
```

四条约束：

1. **默认关闭。** 不开启时服务只绑 `127.0.0.1`，局域网里根本看不到。
2. **严格只读。** 局域网来的请求一律拒绝任何写操作，且只放行白名单里的读路径——
   手机不能碰你的机器。
3. **令牌门控 + 轮换。** 轮换保留 10 分钟宽限窗口，免得手机上开着的页面立刻断掉；
   重置则让旧令牌立即失效。
4. **令牌不进 `settings.json`。** 那个文件是给人看和手改的，密钥单独存。

它解决不了最初那个场景——「去刷手机，跑完了手机提醒你」。那个仍然需要推送。
但它能先验证**你到底会不会在手机上看**，再决定要不要为「主动提醒」付下面那套代价。
